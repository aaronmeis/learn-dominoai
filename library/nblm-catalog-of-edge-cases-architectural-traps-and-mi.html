1. Scope and Analytical Framework

This catalog establishes a technical analysis of architectural traps, operational edge cases, failure modes, and governance risks encountered when evaluating, deploying, or operating the Domino Data Lab enterprise AI platform. The framework is designed to provide direct engineering guidance for enterprise MLOps architects, platform engineers, and architectural review boards evaluating platform placements and infrastructure commitments.

The methodology applied throughout this analysis evaluates platform mechanics through the structural separation between the central Control Plane (UI, API, metadata, model registry, Model Cards, MongoDB metadata stores, RabbitMQ messaging) and distributed Data Planes (Workspaces, Jobs, Apps, and Model API endpoints running on managed Kubernetes clusters) [S2, S3, S4].

All traps, symptoms, root causes, mitigations, and technical assertions in this catalog are grounded exclusively in the primary source context. Where official technical documentation, empirical benchmark data, or regulatory authorization artifacts are absent from the primary literature, this report explicitly logs "SILENCE" rather than extrapolating or inferring unverified platform capabilities.

2. Operational & Environment Traps

2.1 Reproducibility Theater [S4, S5]

  • Symptom: Experiments, notebooks, or candidate production models executed within the platform cannot be reconstructed or re-executed to produce identical outputs at a later date, resulting in severe auditability failures and broken model lineage.
  • Likely Root Cause: Data science teams track source code files or Git commits while failing to pin compute environment images (Docker runtime dependencies) or dataset snapshot versions. Installing packages dynamically via command-line interface (CLI) commands (e.g., pip install or apt-get) inside an active interactive workspace session bypasses environment immutability. This runtime layer modification alters the underlying container without updating the image definition in the Control Plane via the Environment Image Builder, directly violating the design of the Domino Reproducibility Engine (DRE) [S4, S5].
  • Supported Mitigation:
    • Docker Environment Pinning & Image Builder: Define all software dependencies explicitly inside custom compute environments managed by the platform's Environment Image Builder rather than executing ad-hoc CLI package installations at runtime. Standardize on baseline Domino Standard Environments (DSE) or Domino Managed Environments (DME) and publish version-pinned Docker images [S5].
    • Dataset Snapshots: Mandate explicit dataset snapshotting prior to executing data modifications or model training, ensuring code references fixed, immutable data versions rather than unversioned mutable storage directories [S5, S6].
    • Automated Git Commits: Enforce automatic code commits to Git prior to execution, allowing the Domino Reproducibility Engine (DRE) to bind the specific Git commit hash directly to the run metadata in the Control Plane [S4, S6].
    • Model Card Lineage Enforcement: Require all candidate production models to link to an MLflow-backed Model Card that records the exact code commit, environment image digest, workspace configuration, and dataset snapshot IDs [S4, S7].

2.2 Idle GPU & Hardware Tier Cost Overruns [S6]

  • Symptom: Unbudgeted escalation of cloud or data center compute expenditure driven by underutilized hardware resources, particularly dedicated graphics processing units (GPUs).
  • Likely Root Cause: Data scientists open interactive Workspaces (e.g., JupyterLab, VS Code, RStudio) assigned to high-cost GPU hardware tiers and leave sessions active while idle. In terms of Kubernetes infrastructure mechanics, an active interactive Workspace provisions persistent Kubernetes pods bound to underlying node pool allocations. This pod binding prevents cluster autoscalers from scaling down high-cost GPU worker nodes. Conversely, automated background Jobs execute inside ephemeral pods that terminate and release node pool capacity immediately upon completion [S6].
  • Supported Mitigation:
    • Session Lifecycle & Idle Termination Management: Configure administrative lifecycle policies and platform controls to automatically detect idle interactive Workspaces and terminate bound Kubernetes pods after specified inactivity thresholds [S6].
    • Automated Job Scheduling for Heavy Workloads: Shift large-scale model training, hyperparameter tuning, and data processing workloads from interactive Workspaces to scheduled or automated Jobs. Jobs run inside ephemeral Kubernetes pods that terminate immediately upon task completion, releasing underlying node pool resources [S6].
    • Hardware Tier Access Controls & Governance: Enforce Role-Based Access Control (RBAC) policies on hardware tier selection, restricting high-cost GPU hardware tiers to validated training workloads while mandating lightweight CPU tiers for initial code editing and debugging [S6].

2.3 "Any Tool / No Lock-In" vs. System of Record Platform Centricity [S2, S5, S7]

  • Symptom: Architectural teams assume that because Domino hosts open-source IDEs, open languages, and exportable model binaries, the platform can be seamlessly exited or bypassed without workflow disruption, only to encounter severe operational dependency.
  • Likely Root Cause: Conflating artifact portability with metadata portability. While compiled binaries, code files, and Docker container images can be exported to execute on external compute infrastructure, the central lineage history, experiment parameters, Model Card metadata, audit trails, and Model Sentry approval workflows remain natively bound to Domino's MongoDB and Control Plane metadata stores [S2, S4, S7].
  • Supported Mitigation:
    • System of Record Architecture: Explicitly design enterprise platform strategy around the technical reality that Domino's core product value is its centralized System of Record (code + data + environment + parameters), treating open-source IDEs merely as user interfaces [S2, S4].
    • Standardized Handoff Protocols: Define rigid operational boundaries between model development/governance within Domino's Control Plane and downstream prediction endpoints (e.g., AWS SageMaker, Snowflake, Databricks), explicitly documenting which metadata stays within the central control plane [S7].

2.4 Nexus Remote Data Plane Feature Parity Disparities [S3, S8]

  • Symptom: Workloads, web applications, or Model API endpoints fail to deploy or exhibit missing functionality when provisioned across distributed hybrid or multi-region data planes.
  • Likely Root Cause: Attempting to publish Model APIs, Datasets, or web Applications (e.g., Streamlit, Dash, or Shiny applications configured to listen on port 8888 within dedicated data plane pods) onto remote Nexus data planes that historically or structurally lack complete feature parity with the primary Control Plane cluster [S3, S8].
  • Supported Mitigation:
    • Version-Specific Documentation Audit: Mandate a comprehensive architectural review of the installed Domino platform release's Nexus capability matrix prior to designing multi-region remote data plane topologies [S3].
    • Data Plane Target & Isolation Strategy: Align hardware tier targets and application publishing targets strictly with validated remote data plane capabilities, isolating Dev, Staging, and Production environments across dedicated remote data planes or isolated Kubernetes node pools [S7, S8].

3. Governance, Security, and Commercial Claims Traps

Trap / Claim Root Cause & Risk Required Mitigation / Qualification
IL5 / Regulatory Authorization Fallacy [S10] Root Cause: Conflating vendor marketing claims ("deployed in DoD IL5 environments") or program participation with an active, tenant-level authorization.
Risk: Assuming an immediate Authority to Operate (ATO) or DISA Provisional Authorization (PA) exists for a new tenant deployment, exposing the organization to critical regulatory non-compliance [S10].		 Qualification: Classify vendor marketing statements strictly as evidence of vendor program engagement, not an operational authorization for a specific tenant.
Mitigation: Mandate primary DISA PA or FedRAMP package verification URLs for the named offering, and obtain a formal agency-level ATO prior to ingesting controlled unclassified information [S10].
Briefing Percentages as Guaranteed SLAs [S10] Root Cause: Accepting promotional sales briefing figures (e.g., 50% lifecycle speedup, 6× deployment velocity, 40% infrastructure savings, 75% efficiency) as technical performance specifications or contractual Service Level Agreements (SLAs).
Risk: Flawed financial modeling, inaccurate ROI expectations, and invalid capacity planning during enterprise architecture reviews [S10].		 Qualification: Treat vendor percentage claims strictly as promotional sales metrics unsupported by published empirical methodologies in the primary source context [S10].
Mitigation: Disregard vendor percentage metrics in design reviews; establish internal baseline metrics (e.g., job queue latency, workspace idle times) and evaluate operational efficiency through controlled lab tests [S10].
Model Export Equivalence [S7] Root Cause: Assuming that exporting a model artifact to external target environments such as AWS SageMaker, Snowflake, or Databricks transforms those target platforms into functional equivalents of Domino.
Risk: Fragmentation of governance; external target environments lack native integration with Domino's central Model Cards, experiment tracking, and Model Sentry approval workflows, leaving downstream endpoints unmonitored for lineage [S7].		 Qualification: Define model export strictly as a downstream deployment handoff, not an extension of the primary platform.
Mitigation: Maintain Domino's Control Plane as the single System of Record for model lineage, using SageMaker, Snowflake, or Databricks strictly as target prediction endpoints while logging final URLs in the primary Model Card [S4, S7].
