Business Explanation

Business Explanation

Domino is easy to sell as hosted notebooks on GPUs. That sentence will not survive a design review. The picture below is the one that should: a control plane that records, data planes that run, a Project that is the unit of work, and an MLflow path that only exists when code actually logs. Use it to place the GPU and the model card. Use it to refuse a job that already belongs to a lakehouse or an AWS endpoint estate.

How to read it

Read top to bottom, then the purple strip.

  1. Name the consumer. A practitioner opens the UI. A person with a browser hits an App on port 8888 [S8]. Another system hits a Model API [S7].
  2. Control plane records. UI, API, identity, secrets, Mongo/Postgres, Experiment Manager, model registry and cards, Environment image builder. Metadata lives here. The GPU does not [S2] [S41].
  3. Local data plane runs. Workspaces, Jobs, Apps, Model APIs, Datasets, and the data-plane agent as pods. This is where a hardware tier burns money [S2] [S6].
  4. Remote Nexus plane. Compute next to data that cannot move. Same workload types on current versions. Still depends on a live control-plane path [S3] [S21].
  5. Project is the unit. Environment pins the image. Workspace or Job is a client of the Project, not the system of record [S1] [S5].
  6. MLflow is opt-in. No call, no experiment, no card lineage. The Reproducibility Engine is a separate record [S4] [S24] [S25].

Planes

Plane What it holds What it does not hold
Control UI, API, identity, secrets, metadata stores, Experiment Manager, registry, image builder GPU jobs, user kernels, App processes
Local data Workspaces, Jobs, Apps, Model APIs, Datasets, data-plane agent The model card as system of record
Remote Nexus Workspaces, Jobs, Apps, Model APIs, Datasets since 6.0 Starburst sources, Dataset CLI, an independent control plane

Nexus is optional. One control plane, many data planes, any cloud / region / on-prem [S3] [S9] [S11]. If the data already sits next to a lakehouse, the extra plane is coordination cost (Debate 5).

Project lifecycle

Project → Environment → Workspace or Job → experiment (if code logs to MLflow) → model card → Model Sentry → App or Model API.

A model card tracks lineage: code, Environment, workspace settings, datasets [S4]. If the Environment revision that trained the model is gone, the card cannot reconstruct the run. Model Sentry is human review before production. Model Monitoring is drift after deploy. Separate Dev / Staging / Prod data planes are a recommendation, not a law of physics [S7].

When this picture is the wrong one

Already true Better picture
Databricks lakehouse plus Unity Catalog own data and registry Stay on Databricks [S36]
SageMaker endpoints already exist in the AWS account Export is a handoff, not a second home [S7] [S27]
The estate is already OpenShift AI or Kubeflow Operate that stack [S37] [S42]
The ask is an ATO An IL5 sentence on a homepage is not a DISA PA [S10] [S38]

50% lifecycle, 6× development, 40% infra, 75% onboarding are briefing lines [S10]. Repeat a percentage only after measuring your queue (Debate 4).
