Key Concepts & Platform Overview

1. Foundational MLOps Concepts

Before evaluating Domino Data Lab, technical architects must establish clear baseline definitions for fundamental machine learning lifecycle and infrastructure concepts:

  • Model: A mathematical representation learned from data that maps input features to output predictions or decisions.
  • Training vs. Inference: Training is the compute-intensive process of fitting model parameters to historical data. Inference is the operational phase where the trained model evaluates new, unseen input data to generate live predictions.
  • Experiment: A discrete trial consisting of specific code execution, dataset versions, hyperparameter configurations, and environment dependencies used to train and evaluate a candidate model.
  • Registry: A centralized repository used to store, version, document, and govern trained model artifacts across their operational lifecycle.
  • Serving / Endpoint: The hosting infrastructure that exposes a trained model as an accessible network service (e.g., a RESTful API) for real-time or batch inference.
  • MLOps: Machine Learning Operations; the engineering practices, systems, and culture required to automate, operationalize, and govern the transition of ML models from development to production.
  • Governance & Lineage: Governance defines the access controls, review workflows, approval policies, and compliance guardrails regulating model deployment. Lineage tracks the complete provenance of a model artifact—tracing backwards from production to the exact dataset snapshot, code commit, environment image, and parameters that generated it.
  • Reproducibility & Audit Trail: Reproducibility is the technical guarantee that an experiment or model run can be reconstructed to yield identical results. An Audit Trail is an immutable log documenting every operational action, stage transition, and review approval in a model's history.
  • Kubernetes Basics:
    • Cluster: A set of physical or virtual worker machines (nodes) managed as a unified pool of compute resources.
    • Pod: The smallest deployable computing unit in Kubernetes, hosting one or more co-located containers that share storage and network resources.
    • Image: An immutable container template (e.g., Docker image) containing the OS, libraries, tools, and code required to boot a execution environment.

2. Domino Data Lab Core Architecture & Constructs

Domino Data Lab is a Kubernetes-native enterprise AI platform distributed as containerized applications managed via Helm charts and installer scripts. It is validated across cloud-managed Kubernetes services (EKS, AKS, GKE) and self-managed private data center infrastructure.

Core Components & Terminology

  • Project: The fundamental unit of organization and work within Domino. It encapsulates code, datasets, experiment tracking, workspaces, jobs, endpoints, and collaborators.
  • Workspace: An interactive web-based development environment (e.g., Jupyter Notebooks, JupyterLab, VS Code, RStudio, SAS, MATLAB, Cursor) running on a selected Hardware Tier and Compute Environment.
  • Environment: An abstraction layer over a Docker image containing the operating system, language runtimes, system packages, and data science libraries required to boot a Workspace, Job, App, or Model API. Domino distinguishes between Domino Standard Environments (DSE) and Domino Managed Environments (DME).
  • Hardware Tier: Admin-defined compute specifications designating exact CPU, RAM, and GPU allocations assigned to Kubernetes hosting pods.
  • Dataset: Managed storage volumes within Domino supporting snapshot versioning to ensure data consistency across experiment runs.
  • Job: Non-interactive, automated executions running on a dedicated Kubernetes pod (single node or distributed cluster) to process data or train models at scale outside an interactive workspace.
  • Model Registry: An MLflow-backed repository integrated into Domino to discover, track, version, and govern candidate models.
  • Model Card: An integrated document within the Model Registry recording comprehensive metadata, accuracy, fairness/bias reports, and lineage details (code commit, environment version, workspace, dataset snapshot) for compliance and auditing.
  • Model API / Endpoint: A containerized prediction service hosting a registered model artifact behind a hosted RESTful interface.
  • App Hub / Published Apps: The operational application surface enabling data scientists to deploy interactive web tools (e.g., Dash, Streamlit, Shiny, Flask) serving user traffic on designated HTTP ports (typically port 8888).

3. Key Architectural & Operational Mental Models

Control Plane vs. Data Plane

Domino separates administration from execution: * Control Plane: Hosts administrative services, platform APIs, user interfaces, metadata databases, message queues (e.g., RabbitMQ), and central governance logs. * Data Plane: Hosts user execution workloads—interactive Workspaces, background Jobs, distributed training pods, hosted Model APIs, and published Apps where active compute bytes and GPU cycles run.

Domino Nexus (Hybrid Architecture)

Domino Nexus extends platform architecture to support a single, unified Control Plane orchestrating multiple local or remote Data Planes across cloud regions, on-premise data centers, or hybrid cloud environments. Compute workloads are dispatched directly to where the data resides. * Architectural Caveat: Remote data planes historically lacked feature parity with local data planes (e.g., local availability of Model APIs, Apps, or local Datasets). Exact capability matrices must be verified against installed release documentation.

System of Record (SoR)

The core product capability of Domino is its System of Record, not merely hosting cloud IDEs. Complete run reconstruction requires binding four distinct vectors together: $$\text{Reconstructable Run} = \text{Code Commit} + \text{Data Version Snapshot} + \text{Compute Environment Revision} + \text{Hyperparameters}$$

5. Architectural Traps & Edge Cases

  1. Reproducibility Theater: Tracking source code and parameter logs without explicitly pinning exact Docker Environment image revisions and dataset snapshot versions fails to ensure run reconstructability.
  2. Idle Hardware Tier Costs: Interactive Workspaces left running while idle continue to consume dedicated GPU and high-memory Kubernetes pod resources. Financial mitigation requires strict workspace auto-shutdown policies and chargeback reporting.
  3. "Any Tool / No Lock-In" Misconception: While code and exported model artifacts remain open and portable, platform metadata, model card histories, audit trails, and review logs remain native to the Domino Control Plane.
  4. IL5 / Compliance Overclaims: Marketing claims such as "deployed in DoD IL5 environments" reflect vendor program participation or baseline architecture suitability—they do not constitute an official Authority to Operate (ATO) or Provisional Authorization (PA) for a specific customer tenant.
  5. Vendor Marketing Metrics: Vendor briefing figures (e.g., "50% lifecycle reduction," "6× faster," "40% infrastructure savings") represent promotional marketing targets rather than contractual SLAs or guaranteed performance metrics.

Answer Key

  1. Project vs. Workspace vs. Environment: A Project is the top-level organizational container acting as the unit of work (holding code, data links, experiments, and metadata). A Workspace is an interactive, browser-based IDE session (e.g., Jupyter, VS Code) booted on a selected Hardware Tier. An Environment is the underlying Docker image abstraction containing the exact OS binaries, packages, and language libraries that boot inside that workspace.
  2. Control Plane vs. Data Plane: The Control Plane manages administrative services, user access, REST APIs, metadata stores, message queuing (RabbitMQ), and governance records. The Data Plane provides the Kubernetes infrastructure hosting active user compute workloads, including interactive Workspaces, background Jobs, hosted Model APIs, and published Apps.
  3. System of Record Components: True run reconstructability requires recording and pinning four exact artifacts: (1) source code commit revision, (2) dataset snapshot version, (3) compute Environment image revision, and (4) execution hyperparameter settings.
  4. Domino Nexus & Limitations: Domino Nexus is a hybrid architecture allowing a single Control Plane to orchestrate workloads across multiple remote Data Planes in different cloud regions or on-premise clusters. Historically, remote data planes lacked local feature parity, such as hosting local Model APIs, local Apps, or local Dataset management.
  5. Databricks Selection Criteria: Databricks is preferred when an enterprise's data assets, processing pipelines, and data governance are already centralized around a Delta Lake lakehouse and Unity Catalog. Attempting to deploy Domino Nexus on top of Unity Catalog introduces an unnecessary second control plane.
  6. Domino Model Sentry: Model Sentry enforces automated human-in-the-loop review and approval workflows. It locks model transitions between staging environments and production until designated stakeholders approve the metadata, accuracy metrics, and compliance reports attached to the Model Card.
  7. Publish Apps Configuration: Publishing an app (such as Streamlit, Dash, or Shiny) requires configuring an Environment containing the framework libraries, selecting an appropriate Hardware Tier data plane target, and writing application code that serves HTTP traffic on internal port 8888.
  8. IL5 Compliance Verification: A vendor marketing statement regarding IL5 usage reflects general platform capabilities in specific DoD environments. Internal compliance teams require official documentation, such as a formal DISA Provisional Authorization (PA) letter or a specific program Authorization to Operate (ATO) issued for that exact system architecture.
  9. Reproducibility Theater: This refers to the practice of logging source code and metric charts while failing to pin container image versions and data snapshots. Without pinning the compute environment and data state, past experiment results cannot be reliably reconstructed or verified.
  10. Interactive Workspace Risk: Training models inside interactive workspaces risks leaving high-cost GPU resources idle once execution completes if the workspace is left open. Long-running or heavy workloads should instead be submitted as background Jobs, which automatically terminate compute pods upon execution completion.
