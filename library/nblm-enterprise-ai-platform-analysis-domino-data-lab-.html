1. Core Architecture & Structural Mental Models

1.1 Control Plane vs. Data Plane

Domino Data Lab is distributed as a set of containerized, Kubernetes-native applications. Platform deployment, lifecycle orchestration, and system upgrades are managed natively through Helm charts and custom installer utilities executed over Kubernetes clusters [S2]. Structurally, Domino enforces a strict architectural boundary dividing central control plane services from execution workloads running in data planes [S2].

  • Control Plane: Manages administrative workflows, user interfaces, API routing, metadata storage, and orchestration components. Central control services include the Experiment Manager, Model Registry (wrapping open-source MLflow), Environment Image Builder, and core platform messaging queues such as RabbitMQ [S2, S4].
  • Data Plane: Executes compute-heavy data science workloads. The data plane provisions host infrastructure and schedules Kubernetes pods for interactive Workspaces, automated batch Jobs, Published Apps, and real-time Model API inference endpoints [S2, S8].

1.2 The System of Record Model

For enterprise design-review committees, Domino's primary value proposition is not hosting interactive Web IDEs, but serving as a System of Record for data science assets and execution lineage [S4, S13]. As emphasized by MLOps platform leadership, enterprise platforms must transition data science teams away from treating ML development as an unmonitored "laptop research project" to an enterprise, MLflow-backed system of record [S13]. Interactive development environments (Jupyter, RStudio, VS Code) act merely as transitory interface surfaces; the fundamental unit of durable platform value is the Model Card, which captures the complete execution state necessary to reconstruct a run [S4, S7].

Domino enforces transparency and auditability by automatically tracking and linking the four core pillars of execution context: 1. Code: Specific Git commits or project file revisions [S4, S6]. 2. Data: Specific dataset versions or snapshot IDs used during execution [S4, S5]. 3. Environment: Exact Docker image digests and language package definitions [S4, S5]. 4. Parameters & Results: Hyperparameters, execution metrics, and generated artifacts logged via integrated MLflow tracking [S4, S13].

"Domino records the exact code, Environment, Workspace settings, datasets, and data sources for each experiment and associates them with the published model. This data is easily accessible in every model card to help you understand exactly what went into a model and how to reproduce it." [S7]

1.4 Model Factory vs. App Hub

Domino supports two distinct operational paradigms for delivering data science outcomes to consumers:

  • Model Factory: A governed pipeline for building, tracking, registering, and deploying ML models [S4, S7].
  • Delivery Target: Machine-to-machine integration using real-time REST Model APIs, batch inference jobs, or container export pipelines (e.g., to AWS SageMaker, Snowflake, or NVIDIA Fleet Command) [S7].
  • Governance Contract: Managed through Model Cards, human-in-the-loop review workflows (Domino Model Sentry), custom approval stages (Staging, Pre-Production, Production), and automated drift monitoring [S7]. Organization-wide custom stages are configured globally by platform administrators setting the com.cerebro.domino.registeredmodels.stages key in Admin Panel > Advanced > Central Config [S7].
  • App Hub / Publish Apps: A distribution surface for sharing interactive, data-driven web applications with end users [S8, S10].
  • Delivery Target: Human consumer interfaces built using frameworks like Streamlit, Dash, Flask, Shiny, or custom HTTP servers [S8].
  • Execution Surface: Apps execute inside Kubernetes pods on dedicated hardware tiers. Published applications must serve traffic on port 8888 to be correctly routed through Domino's App Launchpad [S8].

2. Terminology & Frequently Confused Concepts

2.1 Project vs. Workspace vs. Compute Environment vs. Hardware Tier

Project The foundational unit of organization, collaboration, and governance in Domino [S1, S6]. It acts as the central umbrella container that stores access control policies, file revisions, experiment logs, dataset links, job schedules, and model cards [S1, S4, S6, S7].

Workspace An interactive compute session hosted in a Web browser [S6]. It provides a developer environment (such as Jupyter, JupyterLab, VS Code, RStudio, SAS, MATLAB, or Cursor) for exploratory data analysis and code development [S1, S6].

Compute Environment A custom Docker image abstraction that defines the execution environment for containers [S5]. It contains operating system packages, system tools, language runtimes, and specific library dependencies (e.g., Domino Standard Environments [DSE] or Domino Minimal Environments [DME]) [S5].

Hardware Tier A resource allocation specification defined by Kubernetes administrators [S5, S6]. It specifies the exact hardware resources (CPU cores, RAM capacity, and GPU counts) allocated to the Kubernetes pod hosting a Workspace, Job, App, or Model API [S2, S5, S6].

2.3 "Any Tool, Open Platform" vs. Platform Lock-in & Semantics

Domino advertises an open platform that supports "any tool, language, or framework" [S1]. However, enterprise architects presenting before design-review committees must enforce two critical distinctions: 1. Tool Semantics Persist: Hosting an IDE or framework inside a Domino Compute Environment does not alter or simplify its underlying operational mechanics [S1, S5]. A tool that requires complex configuration or scaling logic on a local workstation requires those same configurations within a Domino Docker container [S5]. 2. Metadata Retention on Artifact Export: Model artifacts produced within Domino can be exported to external serving environments (such as AWS SageMaker, Snowflake, or NVIDIA Fleet Command) [S7]. However, while the compiled binary or container artifact moves to the external host, the underlying lineage metadata, execution logs, and audit histories remain tied to Domino's System of Record [S2, S5, S7].

4. Common Failure Modes and Operational Traps

4.1 Reproducibility Theater

  • Symptom / Tell: A data scientist re-runs a historical experiment or attempts to promote a model to production, but model outputs, metrics, or predictive behaviors deviate from original run logs despite having tracked code files in Git [S4, S5].
  • Root Cause: Tracking code revisions without strictly pinning the execution Compute Environment (Docker container digest) and Data Snapshot ID [S4, S5]. Unpinned environments default to floating base images (e.g., :latest), allowing underlying OS packages or language dependencies to update silently between executions [S5].
  • Supported Mitigation / Fix: Enforce strict reproducibility policies prior to execution: 1. Pin Compute Environments to explicit, immutable Docker container digests or build IDs [S5]. 2. Take explicit dataset snapshots before running workflows, referencing specific snapshot versions in code rather than unversioned storage paths [S5, S6]. 3. Require all interactive Workspaces to commit changes to Git prior to running production training executions [S6].

4.2 Idle Hardware & GPU Cost Leaks

  • Symptom / Tell: Cloud infrastructure bills display excessive monthly expenditures driven by persistent, high-cost GPU instances (e.g., NVIDIA A100/H100 nodes), while actual compute utilization metrics show prolonged periods of inactivity [S6].
  • Root Cause: Data scientists open interactive Workspaces provisioned on expensive, GPU-backed Hardware Tiers and leave them running idle overnight or over weekends without stopping the session [S6].
  • Supported Mitigation / Fix: 1. Implement automated auto-shutdown policies for idle Workspaces via administrative settings [S6]. 2. Use lower-cost, CPU-only Hardware Tiers for interactive code development, data exploration, and debugging [S6]. 3. Offload compute-heavy training runs to automated batch Jobs, which provision hardware pods on demand and shut down immediately upon run completion [S6].

4.3 Compliance Overclaim vs. Operational Authorization

  • Symptom / Tell: Platform administrators or compliance officers treat marketing phrases (such as "deployed in DoD IL5 environments") or vendor compliance certifications (HIPAA, SOC 2, 21 CFR Part 11) as an immediate, turnkey authorization to process regulated data [S10].
  • Root Cause: Confusing vendor marketing language and SaaS platform certifications with an official deployment-specific Authority to Operate (ATO) or Provisional Authorization (PA) letter [S10].
  • Supported Mitigation / Fix: 1. Distinguish vendor platform claims from customer operational authorizations [S10]. 2. Demand official vendor documentation (e.g., FedRAMP Marketplace packages, DISA Provisional Authorization letters, or third-party SOC 2 Type II audit reports) specific to the deployed environment [S10]. 3. Establish formal governance controls using Domino Model Sentry and custom stage transitions configured via com.cerebro.domino.registeredmodels.stages in Admin Panel > Advanced > Central Config [S7]. 4. Execute an independent security and compliance review for the specific tenant, data plane, and network architecture prior to ingesting sensitive enterprise data [S2, S10].

4.4 Remote Plane Feature Parity Gap

  • Symptom / Tell: A data science team attempts to publish an interactive web application or deploy a real-time Model API onto a remote cloud data plane managed via Nexus, but the deployment fails or option selectors are missing from the UI [S3].
  • Root Cause: Assuming that remote data planes in a Nexus hybrid topology maintain immediate 1:1 feature parity with the primary local data plane [S3]. Historically, remote data planes lagged in support for specific platform features (such as Published Apps, REST Model APIs, or native Datasets) [S3].
  • Supported Mitigation / Fix: 1. Review the installed version's official administrator documentation for Domino Nexus prior to designing multi-region architectures [S3]. 2. Validate remote plane capabilities against operational requirements during architecture design reviews [S3]. 3. If required features are unsupported on remote planes in the deployed version, co-locate Model API and Published App workloads on supported data planes or upgrade the platform installation [S3, S7, S8].
