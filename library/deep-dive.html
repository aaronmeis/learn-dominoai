Business Explanation

Business Explanation

Domino is easy to describe as "hosted Jupyter on GPUs." That description fails the day's falsifier. This note is the sketch you would defend: what a Project contains, where compute runs, what is recorded, and when another platform is better.

1. What it is

Domino Data Lab is an enterprise AI / MLOps platform. The user-guide overview lists languages, IDEs, data sources, and an Environment catalog [S1]. The architecture page is Kubernetes-native, Helm-installed, on EKS / AKS / GKE or self-managed [S2]. Deployment offerings: managed SaaS, self-managed VPC, on-prem, optional Nexus data planes [S9].

The product home calls it an "operating system for AI outcomes" and prints 50% / 6× / 40% / 75% plus "deployed in DoD IL5 environments" [S10]. Those lines stay qualified. They are not the contract.

2. Two planes

Control plane [S2]: Domino UI (Node.js/React), Secrets Vault, Domino API, RabbitMQ, Identity, MongoDB/PostgreSQL metadata, Experiment Manager, Environment Image Builder, Model Registry. Clients reach it over HTTPS.

Data plane [S2]: data plane agent, Cluster Autoscaler, Workspaces, Apps, endpoints, Jobs, distributed compute clusters. Workloads are ephemeral pods. Long-term files sit on external object storage or file shares. Git and an Environment registry sit outside.

This split is the first sentence of a design review. "Where does the GPU live?" is a data-plane question. "Where is the model card?" is a control-plane question.

3. Nexus

Nexus is optional hybrid: one control plane, many data planes, any cloud / region / on-prem [S3] [S11] [S9]. The local data plane (in the control-plane cluster) historically had the full feature set. Remote planes historically lacked Model APIs, Apps, Datasets, Starburst. Re-read the installed 6.2 page before repeating that gap (desk test E5A).

Warrant: if data cannot move, moving the workspace to that plane is the point. If data already sits next to a lakehouse, the extra plane is coordination cost (Debate 5).

4. The unit of work

A Project holds files, Environments, datasets, experiments, models, and Apps [S1].

A Workspace is Jupyter / JupyterLab / VS Code / RStudio / SAS / MATLAB / Cursor on a hardware tier [S6]. That is what users feel. It is a client of the Project, not the system of record (Debate 1).

An Environment is a Docker-image abstraction (DSE vs DME). Every Workspace, Job, App, and Model boots a container. Edits rebuild a revision [S5]. If the revision that trained the model is gone, the card cannot reconstruct the run.

A Job is the non-interactive path. Automate what you just did in the Workspace [S6].

5. System of record

The model registry is MLflow-based [S4]. Chen et al. 2020 is the nearby paper [S14], not a Domino eval.

A model card tracks lineage: code, Environment, workspace settings, datasets [S4]. The day's claim: the reconstructable unit is that context. Evidence still unrun: list every field the card stores (E1A); rebuild a run from a card (E1B, tenant).

Model Sentry is HITL review before production. Model Monitoring is drift after deploy. Separate data planes for Dev / Staging / Prod are a recommendation, not a law of physics [S7].

6. How it reaches users

Model API: package Project files as Flask (Python) or Plumber (R) [S7]. Consumer is another system.

App: Dash / Flask / Streamlit / Shiny / any HTTP on port 8888. Launchpad. HPA, always ≥1 pod. Hardware tier can target a data plane [S8]. Consumer is a person with a browser.

App Hub on the homepage [S10] is the product name. The contract is Publish Apps [S8].

Export targets named in deploy-to-production include SageMaker, Snowflake, Databricks, or a Docker image [S7]. Exporting an artifact is not exporting the platform (Debate 2).

7. Compliance and speed claims

[S10] states ISO 27001, ISO 9001, SOC 2, HIPAA, GDPR, support for 21 CFR Part 11 / Annex 11, and "deployed in DoD IL5 environments."

This pack has no DISA PA letter, no FedRAMP package, and no docs.dominodatalab.com IL5 architecture page. Elicit light found no Domino product paper (E3B run 2026-10-11). Nearby TEE / reproducibility papers do not transfer.

50% lifecycle, 6× development, 40% infra, 75% onboarding are briefing lines. Teach self-serve Environments and elastic hardware. Repeat a percentage only after measuring your queue (Debate 4).

8. When another platform is better

Competitor Wins when
Databricks Lakehouse + Unity Catalog already own data and registry.
SageMaker AWS-native account, endpoints already exist.
OpenShift AI Estate is already OpenShift.
Kubeflow Team will operate CRDs and does not want a commercial control plane.
Dataiku Users are analysts on a visual workbench.

The day's refusal is specific. "We already standardized on X" is a legitimate warrant. "Domino does not do notebooks" is not.

9. Failure modes to name

  • Reproducibility theater: files tracked, Environment revision and data version missing.
  • Idle GPU Workspace.
  • Treating "any tool" as zero exit cost.
  • Treating an IL5 sentence as an ATO.
  • Assuming a remote Nexus plane has local-plane features.
  • Calling App Hub a separate product from Apps without a current docs split.

10. Falsifier

A feature tour that never names the system of record, never splits control plane from data plane, and never names when Databricks, SageMaker, OpenShift AI, Kubeflow, or Dataiku is better.
