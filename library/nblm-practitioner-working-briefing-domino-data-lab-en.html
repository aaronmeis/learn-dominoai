1. Zero-Prior Foundations & Core MLOps Vocabulary

1.1 Non-Vendor MLOps Prerequisites

Evaluating enterprise machine learning operations platforms requires an unequivocal, vendor-agnostic foundation. The following core MLOps and infrastructure terms establish a technical baseline prior to mapping proprietary vendor abstractions:

  • Model: A mathematical and algorithmic artifact generated by training algorithms on historical datasets to capture underlying patterns, enabling automated inference, classification, or generation when provided with new input features.
  • Training vs. Inference: Training is the iterative, compute-heavy execution phase where learning algorithms optimize model parameters against input data. Inference is the operational execution phase where a static, post-training model evaluates live input payloads to yield prediction outputs.
  • Experiment: A discrete, tracked execution run of machine learning code that records hyperparameter choices, source code revisions, input datasets, and resulting evaluation metrics to determine model performance.
  • Model Registry: A centralized system of record designed to catalog, version, store, and govern trained model artifacts, metadata, and lifecycle stage transitions across environments.
  • Serving/Endpoint: The network-accessible service infrastructure (typically exposing a low-latency REST API) that hosts a trained model binary to ingest live inference requests and return prediction payloads.
  • MLOps: The system engineering discipline, operational practices, and tooling frameworks dedicated to automating, standardizing, monitoring, and governing the end-to-end machine learning lifecycle from development through production.
  • Governance: The structural policies, role-based access controls (RBAC), review workflows, and approval mechanisms that enforce regulatory compliance, security boundaries, and quality standards across model development and deployment.
  • Lineage: The immutable, auditable graph capturing the full provenance of a model—linking exact source code commits, dataset snapshots, container runtime configurations, parameters, and author actions.
  • Reproducibility: The technical guarantee that a specific machine learning execution run can be re-executed at a later date using identical code, data snapshots, runtime environments, and parameters to yield computationally equivalent outputs (Albertoni et al. 2023).
  • Audit Trail: An append-only, chronologically organized log capturing system events, stage state transitions, access approvals, and user actions for compliance and forensic verification.
  • Kubernetes at Outline Level:
    • Cluster: A managed collection of physical or virtual compute nodes orchestrated by Kubernetes control services to run containerized workloads.
    • Pod: The smallest deployable computing unit in Kubernetes, wrapping one or more co-located containers sharing storage, network, and execution specs.
    • Image: An immutable, standalone, lightweight package containing application binaries, system libraries, language runtimes, and configuration code required to run a container.

1.2 Domino Core Components Mapping

Domino Data Lab translates these foundational MLOps concepts into specific platform components and mechanisms:

Domino Term Technical Definition Underlying Mechanism / Analogy
Project The foundational unit of organization, access control, and collaboration within the platform. A logical control boundary and metadata aggregation root binding Git refs, block storage snapshots, container hashes, and governance audit trails.
Workspace An interactive, browser-accessible IDE session executing live user code on managed compute. A dedicated Kubernetes pod running a web-accessible IDE (Jupyter, JupyterLab, VS Code, RStudio, SAS, MATLAB, Cursor) mounted to user storage volumes.

Hardware Tier An administrator-defined profile specifying compute allocations for an execution pod. Kubernetes resource requests and limits mapping directly to CPU, RAM, and GPU node allocations or cloud instance pools.
Dataset A versioned file storage directory designed for data science assets, supporting point-in-time state locking. Specialized persistent volume storage backing point-in-time read-only snapshots to guarantee data immutability across training runs.
Job An automated, non-interactive batch script execution running to completion outside a interactive workspace session. A standalone Kubernetes pod or dynamically provisioned worker cluster (Ray/Spark) executing a designated script on a one-time or scheduled trigger.

2. Platform Architecture & Structural Mental Models

2.1 Architectural Plane Separation (Control Plane vs. Data Plane)

Domino is architected as a Kubernetes-native application distributed via Helm charts and managed installers. The platform is validated across managed public cloud services (Amazon EKS, Azure AKS, Google GKE) and self-managed on-premise Kubernetes environments (docs 6.2).

To preserve security boundaries and prevent data exfiltration, Domino enforces a strict architectural separation between administrative control services and worker execution compute:

+-----------------------------------------------------------------------------------+
| CONTROL PLANE |
| (UI, Management APIs, MongoDB/PostgreSQL Metadata, RabbitMQ, MLflow Registry) |
+-----------------------------------------------------------------------------------+ | | Secure Control Channel | (Metadata & Pod Schedulers) v
+-----------------------------------------------------------------------------------+
| DATA PLANE |
| (Execution Workloads: Workspaces, Batch Jobs, Distributed Clusters, Endpoints) |
| * Dataset Bytes, Raw Feature Payloads, and GPU Worker Memory Localized Here * |
+-----------------------------------------------------------------------------------+

Orchestration signals, status telemetry, and metadata pass exclusively over encrypted Control Plane communication channels. Raw dataset bytes, feature payloads, and deep learning model weights remain entirely localized within the Data Plane Kubernetes pods during processing, ensuring heavy data streams never cross into the Control Plane database layers (docs 6.2).

Plane Architecture Description, Services, and Workload Placement
Control Plane (UI / API / Metadata) Hosts management UI components, central APIs, user authentication, RabbitMQ messaging queues, execution schedulers, the Environment Image Builder, Experiment Manager, and core metadata repositories. The Control Plane orchestrates execution state and captures lineage, but never processes raw user training data bytes.
Data Plane (Execution Compute) Hosts execution workloads within managed Kubernetes pods. Interactive Workspaces, batch Jobs, distributed Ray/Spark clusters, Published Apps, and live Model API serving endpoints execute strictly within the Data Plane. Compute cycles, physical memory, GPU hardware, and persistent volume storage reside entirely here.

2.2 Hybrid Topology (Domino Nexus)

Domino Nexus extends this plane separation by allowing a single centralized Control Plane to govern multiple execution Data Planes distributed across multi-cloud regions, VPCs, and on-premise data centers (docs 6.2).

 +--------------------------------+ | Central Control Plane | | (Unified System of Record) | +--------------------------------+ | +---------------------------+---------------------------+ | | | v v v
+-------------------+ +-------------------+ +-------------------+
| Data Plane 1 | | Data Plane 2 | | Data Plane 3 |
| On-Prem Cluster | | AWS EKS VPC | | Azure AKS VPC |
+-------------------+ +-------------------+ +-------------------+

Explicit System Silence & Version Warning: Remote data planes historically or version-dependently may lack complete feature parity with local data planes—specifically regarding localized Model API hosting, direct App Hub publishing, or local Dataset storage (docs 6.2). System architects must verify the capability matrix against their exact platform release (docs 6.2) during cross-cluster architectural design reviews ([S3]).

2.3 The System of Record Claim

Domino operates as an enterprise System of Record for AI assets, establishing a clear architectural boundary between transient code execution (e.g., local Jupyter notebooks) and immutable, auditable lineage management.

The platform enforces technical auditability through a strict four-part reconstructable run equation:

System of Record Execution Equation

$$\text{Reconstructable Run} = \text{Code (Git commit)} + \text{Data Snapshot} + \text{Environment Revision (Docker Image)} + \text{Parameters}$$

By automatically binding these four vectors at execution time, Domino creates an immutable record that allows any historical experiment, job, or deployment to be precisely reconstructed and verified for governance audits.

3. The Governed Model Lifecycle (Project to Production)

3.1 Step-by-Step Lifecycle Sequence

[Step 1: Workspace Dev] ---> [Step 2: Training & Jobs] ---> [Step 3: Registration & Card] |
[Step 5: Production Deploy] <--- [Step 4: Governance & Sentry] <--------+

Step 1: Project Initialization & Workspace Setup

  • Operational Mechanism: The practitioner creates a Project (the logical governance boundary) and launches an interactive Workspace session (e.g., VS Code or JupyterLab). The user selects a specific Compute Environment (e.g., Domino Standard Environment) and Hardware Tier.
  • Plane Location: Data Plane (Kubernetes pod hosting the interactive IDE environment).
  • Recorded Metadata: Control Plane records user ID, workspace session ID, target hardware tier allocation, base environment revision hash, and session launch timestamps.

Step 2: Model Training & Experimentation

  • Operational Mechanism: Following initial prototyping in a workspace, the user schedules non-interactive batch Jobs or spins up distributed compute frameworks (Ray or Apache Spark). Rather than relying on static hardware allocations, distributed Ray and Spark clusters are provisioned dynamically on-demand within the Data Plane via dedicated Kubernetes operators, scaling worker pods across available node pools.
  • Plane Location: Data Plane (batch Job pods and dynamic Ray/Spark worker nodes).
  • Recorded Metadata: Control Plane captures the exact Git commit SHA, dataset snapshot IDs, environment Docker image digest, execution parameters, stdout/stderr logs, hardware utilization metrics, and MLflow evaluation metrics (docs 6.2).

Step 3: Model Registration & Model Card Creation

  • Operational Mechanism: The user registers a candidate model binary into the MLflow-backed Model Registry. Domino automatically generates a structured Model Card that aggregates the complete execution provenance (docs 5.8/6.2).
  • Plane Location: Control Plane (MLflow registry metadata engine and Model Card store).
  • Recorded Metadata: Model Card captures model binaries, source Git SHA, dataset snapshot references, exact container environment digest, training parameters, bias/explainability metrics, and author identity.

Step 4: Governance, Review, and Approval (Model Sentry)

  • Operational Mechanism: The candidate model undergoes human-in-the-loop review managed by Model Sentry. Requesters initiate stage transitions (e.g., Staging, Pre-Production, Production, or custom organizational stages). Designated reviewers inspect the Model Card, test live endpoints, or launch an ephemeral audit workspace to validate model behavior. Project Owners retain manual stage-override authority (docs 5.8).
  • Plane Location: Control Plane (Model Sentry access engine and workflow service).
  • Recorded Metadata: Audit log records review requests, reviewer comments, formal approval/rejection signatures, stage transition timestamps, and any manual override events executed by Project Owners.

Step 5: Production Deployment

  • Operational Mechanism: Approved models are published as REST-based Model API endpoints or embedded within interactive applications published to the App Hub (exposed on port 8888). Alternatively, containerized model binaries are exported to external target platforms (Amazon SageMaker, Snowflake, NVIDIA Fleet Command, or enterprise CI/CD pipelines) (docs 5.8/6.2).
  • Plane Location: Data Plane (for native Model APIs and Published Apps) or External Target Infrastructure (for exported container artifacts).
  • Recorded Metadata: Control Plane records active deployment states, REST endpoint URIs, serving pod resource configurations, target data plane routing paths, and export audit trails.

3.2 Environments Separation Best Practices

Organizations deploying models across Dev, Staging, and Production environments typically select one of two infrastructure isolation patterns (docs 5.8):

  1. Separate Data Planes (Recommended): Leverages Domino Nexus to map Dev, Staging, and Production to physically distinct Kubernetes clusters. While Node Pool Isolation satisfies compute resource boundaries within a single cluster, only Separate Data Planes eliminate Control Plane blast radius and ensure total isolation required for air-gapped compliance and strict production access controls (docs 5.8).
  2. Node Pool Isolation: Collocates Dev, Staging, and Production workloads within a single Kubernetes cluster using dedicated, isolated Node Pools. Isolates worker VMs and container pods at the infrastructure compute tier while sharing underlying cluster control services.

5. Operational Traps, Edge Cases, and Governance Fallacies

5.1 Operational Traps Matrix

Trap Name Symptom / Tell Root Cause Practitioner Fix
Reproducibility Theater Source script files are tracked in Git, but historical execution runs cannot be reproduced or yield drifting results. Tracking code files while relying on unpinned, manual runtime installations (pip install) inside active workspaces. Simple Git tracking fails because base environment container layers and dependencies remain mutable without immutable Docker image digests and dataset snapshots (docs 6.2). Enforce the Domino Reproducibility Engine (DRE) by pinning immutable Docker image digests via the Environment Image Builder and enforcing dataset snapshot locking prior to training runs (docs 5.8/6.2).
Idle Hardware Cost Spikes Infrastructure expenditures spike sharply due to idle, unutilized GPU compute node allocations. Data science practitioners leave interactive GPU-bound Workspaces active overnight or over weekends without running active computations (docs 6.2). Configure automated workspace auto-shutdown timeouts in administrator settings and establish hardware tier cost-tracking rules.
The "Any Tool / No Lock-In" Illusion Engineering leaders assume platform exportability erases long-term platform reliance. Confusing open-source language and IDE compatibility with zero platform infrastructure dependency. Recognize that while trained model binaries export cleanly to SageMaker or Snowflake, Domino's system of record metadata, audit trails, and Model Cards remain anchored in the Control Plane (docs 5.8).
Remote Nexus Plane Disparity Model APIs or Published Apps fail to deploy when targeted to a remote Nexus Data Plane. Assuming total feature parity across all remote data planes without checking version-specific service support (docs 6.2). Audit installed platform version documentation (docs 6.2) to verify whether remote data planes support localized Model APIs, Apps, or Datasets before finalizing cross-plane architectures.

5.2 Compliance and Marketing Overclaim Disambiguation

Architects must maintain technical accuracy by separating vendor marketing language from architectural reality:

  • Compliance Claims vs. Authorization to Operate (ATO): Marketing statements indicating that Domino is "deployed in DoD IL5 environments" or displaying HIPAA, SOC 2, and 21 CFR Part 11 vendor badges ([S10]) reflect program eligibility and platform capability. They do not constitute a turnkey Provisional Authorization (PA) or Authority to Operate (ATO) for a customer's specific lab instance. An official ATO requires a dedicated government authorization package for that specific deployment.
  • Vendor Productivity Metrics: Published marketing percentages (e.g., "6x faster deployment," "40% infrastructure savings," "50%," "75%") are vendor briefing claims ([S10]). They are not contractual SLAs or guaranteed performance benchmarks. Technical teams must evaluate pipeline latencies and compute costs within their own operational environments.
